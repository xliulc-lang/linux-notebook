# 文本三剑客与日志分析实战：6 大工业级排障关卡

> **背景设定**：你刚刚入职某大厂核心交易研发组，今天早上 09:30，监控大盘突然报警：“订单支付服务 5xx 错误率飙升，同时部分接口响应时延超过 2 秒！”。  
> 生产环境没有图形界面，只有只读 SSH 终端权限。你需要使用 **grep、awk、sed、sort、uniq、find、管道重定向** 等命令在 5 分钟内快速定位问题根因并输出统计报告。

---

## 关卡 1：【应急排障】定位 5xx 错误突发接口与调用异常

- **业务背景**：监控大盘报 5xx 突增，首先要确认是哪个接口在报错，以及报错的具体堆栈信息。
- **任务目标**：
  1. 从 `nginx_access.log` 中找出所有 HTTP 状态码为 `500` 或 `502` 或 `504` 的请求，仅打印其**请求时间、接口 URL、状态码和 trace_id**。
  2. 统计这些 5xx 错误中，**哪个接口 URL 报错次数最多？**
  3. 从 `application.log` 中找出出现 `SQLException` 错误行的**前 1 行和后 2 行上下文**（避免只看到错误看不到原因）。
- **核心考点**：
  - `grep -E`（扩展正则多条件匹配）
  - `awk` 指定空格为分隔符提取特定列
  - `sort | uniq -c | sort -nr`（经典词频统计流水线）
  - `grep -B -A` 或 `grep -C`（打印上下文行）

---

## 关卡 2：【流量画像】统计 Top 客户端 IP 与 API 访问排行榜

- **业务背景**：安全组怀疑有爬虫或恶意流量在刷接口，要求研发统计流量来源。
- **任务目标**：
  1. 统计访问量最高的前 3 个客户端 IP，并输出访问次数和 IP。
  2. 统计所有非 200 状态码（如 400、401、404、500 等）的分布计数（哪个错误状态码出现最多？）。
  3. 过滤掉健康检查接口（`/api/v1/health`），统计访问量最大的 Top 3 业务 API。
- **核心考点**：
  - `awk` 的列过滤与模式匹配（`$9 != 200`）
  - `grep -v` 反向排除健康检查干扰

---

## 关卡 3：【性能瓶颈】慢请求分析与接口平均耗时统计

- **业务背景**：SLA 规定接口耗时必须在 800ms 以内。需要抓出耗时大于等于 1.0 秒（`1.000`）的所有长尾请求，并计算慢请求的各接口平均耗时。
- **日志字段解析**（`nginx_access.log`）：
  - 第 7 列：URL（如 `/api/v1/order/pay`）
  - 第 9 列：状态码（如 `200` 或 `500`）
  - 第 11 列：请求耗时（单位：秒，如 `1.450`）
- **任务目标**：
  1. 提取所有耗时 `>= 1.000` 秒的慢请求，按耗时从大到小倒序排序，输出最慢的前 5 条（打印：耗时、URL、状态码）。
  2. **【高阶挑战 - 纯 awk 编程】**：使用单条 `awk` 脚本，分组计算各个不同 URL 的**请求总次数**以及**平均耗时（保留 3 位小数）**，并按平均耗时降序排列！
- **核心考点**：
  - `awk` 浮点数条件判断（`$11 >= 1.0`）
  - `sort -k 1,1 -nr`（按指定列进行数值倒序排序）
  - `awk` 的关联数组（`sum[$7] += $11; count[$7]++`）与 `END` 块遍历

---

## 关卡 4：【数据合规】敏感信息批量正则脱敏（sed 流编辑）

- **业务背景**：研发需要把 `application.log` 导出拷贝给外部供应商进行离线分析。根据合规与隐私保护法，**必须对日志中包含的 11 位手机号和 18 位身份证号进行脱敏掩码**。
  - 手机号规则：`13812345678` -> `138****5678`（保留前 3 后 4，中间 4 位用 `*` 代替）。
  - 身份证号规则：`110101199003072345` -> `110101********2345`（保留前 6 后 4，中间 8 位用 `*` 代替）。
- **任务目标**：
  1. 使用单行 `sed` 正则命令，将 `application.log` 中的所有手机号和身份证号完成脱敏，输出并保存为 `application_masked.log`。
  2. 验证：用 `grep` 检查是否还存在明文手机号。
- **核心考点**：
  - `sed -E` 扩展正则表达式
  - 正则分组捕获与反向引用：`\1****\3`
  - `sed` 的原地修改（`-i`）与流输出

---

## 关卡 5：【全链路排障】TraceID 跨服务级联追踪（xargs 联动）

- **业务背景**：微服务架构下，一个外部请求会分配唯一的 `trace_id`。当在网关看到某次请求失败时，需要拿着这个 `trace_id` 去后端 `application.log` 里把全流程日志抓出来。
- **任务目标**：
  1. 从 `nginx_access.log` 中找出第一个发生 `502` 错误的请求的 `trace_id`。
  2. 将获取到的 `trace_id` 通过管道传递给 `xargs`，瞬间从 `application.log` 中检索出与该 `trace_id` 相关的所有业务日志与异常堆栈。
- **核心考点**：
  - `grep` 正则提取（`-oP` 或 awk）
  - `head -n 1`
  - `xargs -I {} grep {} application.log`

---

## 关卡 6：【管道重定向艺术】多路分流与错误合流

- **业务背景**：编写日常巡检脚本时，常常需要：既在终端实时看到屏幕输出，又把普通输出和错误输出分流保存到不同文件。
- **任务目标**：
  1. 使用 `tee` 命令，实现一条命令把分析结果同时打印在屏幕上，并保存到文件 `report.txt`。
  2. 彻底理解并演示：`command > out.log 2>&1` 与 `command 2>&1 > out.log` 的致命区别！
- **核心考点**：
  - `tee` 命令
  - 文件描述符重定向的从左到右求值顺序
