## 一、 核心概念与底层存储原理

在 Linux 文件系统中（如 ext4），理解链接的关键在于搞清楚三者的关系：
1. **目录项（dentry）**：记录“文件名”与“inode 编号”的映射关系。
2. **inode（索引节点）**：存储文件的**元数据**（权限、所有者、文件大小、创建/修改时间、**硬链接计数**、指向数据块的指针）。
3. **数据块（Data Block）**：实际存储文件内容的物理/逻辑磁盘块。

### 1. 硬链接（Hard Link）
* **本质**：同一个 inode 的另一个别名（别称）。
* **底层**：只是在目录中新建了一个文件名映射到**相同的 inode 编号**，同时让该 inode 的“硬链接计数（Hard link count）”加 1。
* **特性**：
  * 删除源文件名，硬链接**完全不受影响**，只要硬链接计数不为 0，数据块就不会被回收。
  * **不能跨文件系统**（因为不同文件系统的 inode 号相互独立且可能冲突）。
  * **不能对目录创建硬链接**（防止在文件系统目录树中形成循环环路，导致遍历死循环）。

### 2. 软链接（Symbolic Link / 符号链接）
* **本质**：一个特殊类型的**全新独立文件**（拥有自己独立的 inode）。
* **底层**：它的数据块里只存放了一串文本——**目标文件的路径字符串**（类似 Windows 的“快捷方式”）。
* **特性**：
  * 可以跨文件系统、可以指向不存在的文件（称为悬空链接/断链）、**可以指向目录**。
  * 若删除了源文件，软链接失效（变成红色的断链）；若重建同名源文件，软链接自动复活。

## 二、 软、硬链接全方位对比矩阵（面试直背）

| 对比维度 | 硬链接（Hard Link） | 软链接（Symbolic Link） |
| :--- | :--- | :--- |
| **创建命令** | `ln source target` | `ln -s source target` |
| **inode 编号** | **完全相同**（共享同一个 inode） | **全新独立**（分配新 inode） |
| **磁盘空间占用** | 不占额外数据块（只占微小的目录项空间） | 占用独立 inode 和存放路径字符串的数据块 |
| **是否能跨文件系统** | ❌ 严禁跨文件系统（跨挂载点） | ✅ 可以跨文件系统/网络挂载点 |
| **是否能对目录创建** | ❌ 普通用户严禁对目录建硬链接 | ✅ 广泛用于目录快捷方式 |
| **源文件被删除时** | 内容依然完全可读（硬链接数减 1） | 变成无效的**悬空链接（Dangling Link）** |
| **工业核心应用场景** | **极速增量快照备份（Time Machine/Git）**、防止误删核心数据 | **动态库多版本管理（SONAME 机制）**、平滑升级/回滚、路径别名 |

### 实验一：Linux 动态库 SONAME 多版本平滑升级与热回滚
* **目录**：`part1_soname_demo/`
* **场景还原**：Linux 系统的 `glibc`（如 `libc.so.6 -> libc-2.31.so`）为何大量采用软链接链条？
* **实验内容**：
  1. 编译 C++ 动态库 V1.0.0；
  2. 建立 `libmath.so -> libmath.so.1 -> libmath.so.1.0.0` 软链接体系；
  3. 编译主程序 `main` 链接该库；
  4. **在完全不重新编译 main 的情况下**，编译 V2.0.0 动态库并切换软链接，实现一秒无缝平滑升级与一键故障回滚！
* **执行命令**：
  ```bash
  cd part1_soname_demo
  chmod +x run_soname_demo.sh
  ./run_soname_demo.sh
  ```

### 实验二：硬链接在极速增量快照备份中的应用（Time Machine 原理）
* **目录**：`part2_snapshot_backup/`
* **场景还原**：大型代码仓备份或 Docker 镜像分层时，如何做到“秒级创建快照、未修改的大文件零占用额外磁盘空间”？
* **实验内容**：
  1. 创建包含 10MB 大资产文件的原始工程；
  2. 使用 `cp -al`（基于硬链接）秒级生成 Day1 快照，验证磁盘新增占用为 0；
  3. 第二天修改部分代码，生成 Day2 快照；
  4. 验证：修改的文件自动分离拥有独立 inode，未修改的大文件链接数变为 3，共享同一块物理磁盘。
* **执行命令**：
  ```bash

  ./run_snapshot_demo.sh
  ```

### 实验三：排查“文件已被 rm 删除，但磁盘空间未释放”生产故障
* **目录**：`part3_deleted_leak_demo/`
* **场景还原**：线上服务器 50GB 日志塞满磁盘，运维直接 `rm -f app.log`，但 `df -h` 显示磁盘依然 100% 满！为什么？怎么查？
* **实验原理**：Linux 内核中，只有当文件的**硬链接计数归 0** 并且 **进程打开的句柄引用计数归 0** 时，数据块才会被释放！
* **实验内容**：
  1. 启动一个后台进程，打开大文件并保持句柄；
  2. 模拟误删文件后，使用 `lsof | grep deleted` 揪出罪魁祸首进程；
  3. 掌握线上免重启自救技巧：通过 `/proc/<PID>/fd/<FD>` 清空释放磁盘空间。
* **执行命令**：
  ```bash
  cd part3_deleted_leak_demo
  chmod +x run_leak_demo.sh
  ./run_leak_demo.sh
  ```
